# Audyt strony r352.com - 2026-06-05

## Podsumowanie

Strona ma mocny fundament strategiczny: spójny positioning, rozbudowane SEO komponentowe, sitemap, robots, llms.txt, schema.org, dobre case studies i sensowną architekturę Vite/React. Największe problemy nie są w samej treści, tylko w warstwie publikacji i renderowania: canonicale wskazują inny host niż faktycznie używany, brakujące assety social/favicon są maskowane przez SPA rewrite, a część SEO zależy od JavaScriptu.

Priorytet napraw:

1. Ujednolicić host canonical: albo wszystko na `https://www.r352.com`, albo wyłączyć przekierowanie na `www` i wrócić do `https://r352.com`.
2. Dodać realne pliki `/og-image.png`, `/favicon.svg`, `/apple-touch-icon.png` albo poprawić ich URL-e.
3. Poprawić rewrite na Vercel tak, aby brakujące pliki assetów zwracały 404, a nie `index.html`.
4. Usunąć lub realnie wdrożyć `/pl`, bo obecny `hreflang` deklaruje polską wersję, której crawler nie dostaje jako osobnej strony.
5. Zmniejszyć największe assety i odchudzić initial JS/CSS.

## Co sprawdziłem

- Lokalny build: `npm run build` przechodzi poprawnie.
- Publiczne HTTP: `https://r352.com` zwraca `307` do `https://www.r352.com/`.
- Live HTML: fallback metadata nadal wskazują `https://r352.com`.
- Live robots/sitemap: dostępne, ale sitemap i robots wskazują non-www.
- Live assety: `/og-image.png`, `/favicon.svg`, `/apple-touch-icon.png` zwracają `200`, ale jako `text/html` z `index.html`, nie jako obraz/ikona.
- Lokalna struktura: Vite + React + wouter, dużo katalogów `dist-check-*`, publiczne wideo i sekwencje klatek.

## Krytyczne problemy

### 1. Rozjazd domeny canonical vs live host

Live:

- `https://r352.com` -> `307` -> `https://www.r352.com/`
- HTML ma canonical `https://r352.com`
- sitemap ma URL-e `https://r352.com/...`
- robots ma `Sitemap: https://r352.com/sitemap.xml`
- schema.org używa `https://r352.com`

Źródła w kodzie:

- `index.html:10-15`
- `src/app/components/SEO.tsx:16-20`
- `src/app/components/SEO.tsx:38-45`
- `src/app/components/SEO.tsx:66-71`
- `public/sitemap.xml`
- `public/robots.txt`

Ryzyko: Google i LLM crawlery dostają mieszane sygnały encji i kanoniczności. To nie musi zabić indeksacji, ale rozmywa autorytet adresu, szczególnie przy brandzie, który chce budować rozpoznawalność jako `r352`.

Rekomendacja: wybrać jeden host. Ponieważ Vercel obecnie wymusza `www`, najszybsza naprawa to zmienić `baseUrl` i wszystkie fallback URL-e na `https://www.r352.com`, sitemap i robots również. Alternatywnie zmienić konfigurację domeny w Vercel, żeby `www` przekierowywało do apex.

### 2. Brakujące OG/favicon/apple icon są maskowane przez SPA rewrite

Live status:

- `https://www.r352.com/og-image.png` -> `200`, ale `content-type: text/html`
- `https://www.r352.com/favicon.svg` -> `200`, ale `content-type: text/html`
- `https://www.r352.com/apple-touch-icon.png` -> `200`, ale `content-type: text/html`

Źródła w kodzie:

- `index.html:23`
- `index.html:31`
- `index.html:48-49`
- `src/app/components/SEO.tsx:16`
- `src/app/components/SEO.tsx:39`
- `src/app/components/SEO.tsx:71`
- `src/app/components/SEO.tsx:253`

W `public/` istnieje `logo.svg`, ale nie ma `og-image.png`, `favicon.svg`, `apple-touch-icon.png`.

Ryzyko: social preview, Twitter Card, schema logo, favicon i ikona iOS mogą być uszkodzone mimo pozornych statusów 200. Dodatkowo cache dla `.png`/`.svg` jest immutable, więc błędny HTML pod obrazem może trzymać się długo.

Rekomendacja: dodać realne pliki do `public/`, najlepiej:

- `public/og-image.png` 1200 x 630
- `public/favicon.svg`
- `public/apple-touch-icon.png` 180 x 180
- opcjonalnie `public/manifest.webmanifest`

### 3. Rewrite łapie wszystko, także brakujące pliki

Źródło:

- `vercel.json:2-4`

Konfiguracja:

```json
{ "source": "/(.*)", "destination": "/index.html" }
```

To jest wygodne dla SPA, ale niebezpieczne dla assetów. Brakujące obrazy, ikony i potencjalnie inne pliki zwracają `index.html`, a nagłówki dla rozszerzeń ustawiają cache immutable.

Ryzyko: crawlers, social scrapers i browser cache dostają fałszywe 200. Monitoring też może nie złapać brakujących assetów.

Rekomendacja: dodać reguły tak, aby routing SPA dotyczył tylko dokumentów, a nie plików z rozszerzeniami. Minimalnie: osobne rewrites/headers dla istniejących assetów i fallback tylko dla ścieżek bez kropki. Na Vercel warto przetestować regułę typu `/:path*` z warunkiem braku rozszerzenia lub zastosować frameworkowy fallback.

### 4. `hreflang` deklaruje `/pl`, ale aplikacja nie ma trasy `/pl`

Źródła:

- `index.html:13-15`
- `src/app/components/SEO.tsx:272-275`
- `src/app/App.tsx:213-245`
- `src/app/context/LanguageContext.tsx:22-24`

Język działa jako stan Reacta, domyślnie EN. Nie ma route `/pl`, `/pl/services`, itd. Live `/pl` zwraca `index.html`, ale po stronie klienta wpada w 404, bo nie ma pasującej trasy.

Ryzyko: Google dostaje deklarację alternatywnej wersji językowej, która nie istnieje jako indeksowalny dokument. To może osłabić zaufanie do hreflang i wprowadzać błędne adresy do indeksu.

Rekomendacja:

- Opcja szybka: usunąć `hreflang="pl"` do czasu wdrożenia URL-i językowych.
- Opcja docelowa: dodać routing `/pl`, `/pl/services`, `/pl/work`, itd., wykrywać język z URL-a i generować osobne canonicale.

## SEO i indeksacja

### Mocne strony

- Jest sitemap i robots.
- Jest `llms.txt`.
- Jest rozbudowane schema.org: Person, Organization, WebSite, ProfessionalService, FAQ, BlogPosting.
- Każda główna trasa ma unikalne title/description w `getPageSEO`.
- Sitemap zawiera core pages, case studies, journal i service details.

### Problemy

1. Fallback HTML z `index.html` jest jedynym statycznym dokumentem dla wszystkich tras. Metadane per-route pojawiają się dopiero po JS przez `react-helmet-async`. Dla crawlerów bez renderowania JS wszystkie podstrony wyglądają jak homepage.
2. `og:image` domyślnie wskazuje brakujący plik.
3. `Organization.logo` wskazuje OG image zamiast prawdziwego logo.
4. `FAQPage` na homepage może być ryzykowne, jeżeli pytania/odpowiedzi nie są widoczne na stronie w takiej samej formie. Schema powinna odpowiadać widocznej treści.
5. `reviewsSchema` i `aggregateRating` wymagają ostrożności: recenzje powinny być realnie widoczne, udokumentowane i zgodne z politykami rich results.

Rekomendacja strategiczna: jeśli SEO/LLM discovery jest ważne, rozważyć prerender/SSG dla głównych tras. Przy Vite można użyć prerenderingu, albo przenieść marketingowe strony do frameworka z SSG/SSR. Największy zysk: prawdziwe HTML dla `/services`, `/process`, `/glossary`, `/work/*`, `/journal/*`.

## Performance

Build przechodzi, ale największe ryzyka:

- `dist/assets/bkg1 2-*.png` około 9.1 MB
- `RP4` około 4.5 MB
- `BP4` około 3.3 MB
- kilka kolejnych PNG 1-2.6 MB
- `dist` po buildzie około 77 MB
- `public/videos` około 8.8 MB
- `public/scroll-frames` około 5.1 MB
- `public/scroll-frames-light` około 2.1 MB
- główny JS `index-*.js` około 429 KB, gzip 127 KB
- CSS `index-*.css` około 278 KB, gzip 47 KB
- `jspdf` i `html2canvas` są osobnymi ciężkimi chunkami, co jest dobre, ale trzeba pilnować, żeby nie ładowały się na zwykłych marketingowych trasach.

Rekomendacje:

1. Skonwertować największe PNG do AVIF/WebP i użyć responsive sizes.
2. Przejrzeć, czy duże assety są importowane na homepage lub przez komponenty globalne.
3. Dodać budżety bundle size w CI lub prosty skrypt raportujący top 20 assetów.
4. Ograniczyć zewnętrzne fonty: obecnie ładowane są Fontshare, cdnfonts i Google Fonts. Każdy dodatkowy CDN to koszt DNS/TLS i ryzyko FOUT/FOIT.
5. Preloader blokuje body na start przez około 800 ms plus animację. Efekt jest premium, ale może pogarszać perceived performance i Core Web Vitals.

## UX / konwersja

Mocne strony:

- Bardzo wyrazisty positioning: design partner, operating system, r3loop.
- Jest wiele ścieżek kontaktu: brief, Calendly, mail.
- Case studies, services, process i glossary dobrze budują kategorię.
- Floating CTA i chat mogą wspierać konwersję.

Ryzyka:

1. Zbyt dużo globalnych efektów nad każdą stroną: preloader, smooth scroll, cursor glow, custom cursor, persistent background, bottom gradient, floating CTA, chatbot. Na desktopie może to wyglądać premium, ale na mobile i słabszych urządzeniach może obciążać uwagę i wydajność.
2. Header ma `pointer-events-none` gdy nie jest scrolled, z wyjątkami na elementach. W praktyce to może powodować trudne do debugowania edge case'y interakcji.
3. Przełącznik języka nie aktualizuje URL-a, więc użytkownik nie może wysłać linku do polskiej wersji tej samej strony.
4. Strony `limitedaccess*` są routowane publicznie i część z nich ma treści ofertowe. Jeśli to są materiały prywatne, powinny być poza sitemap i najlepiej chronione po stronie serwera, nie tylko hasłem w kliencie.

## Accessibility

Plusy:

- Wiele przycisków ma `aria-label`.
- Obrazy case studies mają alty.
- Elementy dekoracyjne często mają `aria-hidden`.

Ryzyka:

1. Custom cursor i motion-heavy UI powinny być w pełni wyłączalne przy `prefers-reduced-motion`.
2. Smooth scroll i animowane przejścia mogą przeszkadzać użytkownikom klawiatury/screen readerów, jeśli focus nie jest zarządzany po zmianie route.
3. Mobile menu powinno mieć `aria-expanded`, `aria-controls` i focus trap.
4. Chatbot/floating CTA mogą konkurować z główną nawigacją na małych ekranach.

## Analityka i privacy

GTM jest wstrzykiwany przez React po mount:

- `src/app/components/GTM.tsx`

Plus: nie blokuje statycznego HTML.

Ryzyko: brak widocznej warstwy consent/cookies w kodzie, a GTM może ładować narzędzia wymagające zgody w UE. Przy lokalizacji w Hiszpanii/Mallorce warto sprawdzić zgodność z ePrivacy/GDPR.
