Priorytet napraw

  1. Ujednolicić host canonical: wszystko na https://www.r352.com albo wyłączyć przekierowanie na www i wrócić do https://r352.com.
  2. Dodać realne pliki /og-image.png, /favicon.svg, /apple-touch-icon.png albo poprawić ich URL-e.
  3. Poprawić rewrite na Vercel tak, aby brakujące pliki assetów zwracały 404, a nie index.html.
  4. Usunąć lub realnie wdrożyć /pl, bo obecny hreflang deklaruje polską wersję, której crawler nie dostaje jako osobnej strony.
  5. Zmniejszyć największe assety i odchudzić initial JS/CSS.

Co sprawdziłem

  • Lokalny build: npm run build przechodzi poprawnie.
  • Publiczne HTTP: https://r352.com zwraca 307 do https://www.r352.com/.
  • Live HTML: fallback metadata nadal wskazują https://r352.com.

Krytyczne problemy

1. Rozjazd domeny canonical vs live host

Krytyczne SEO Indeksacja

Live:

  • https://r352.com -> 307 -> https://www.r352.com/
  • HTML ma canonical https://r352.com
  • sitemap ma URL-e https://r352.com/...
  • robots ma Sitemap: https://r352.com/sitemap.xml
  • schema.org używa https://r352.com

Ryzyko: Google i LLM crawlery dostają mieszane sygnały encji i kanoniczności. To może rozmywać autorytet adresu i brandu.

Rekomendacja: wybrać jeden host. Ponieważ Vercel obecnie wymusza www, najszybsza naprawa to zmienić baseUrl, fallback URL-e, sitemap i robots na https://www.r352.com.

2. Brakujące OG/favicon/apple icon

Krytyczne Social preview Assety

Live status:

  • https://www.r352.com/og-image.png -> 200, ale text/html
  • https://www.r352.com/favicon.svg -> 200, ale text/html
  • https://www.r352.com/apple-touch-icon.png -> 200, ale text/html

W public/ istnieje logo.svg, ale nie ma og-image.png, favicon.svg, apple-touch-icon.png.

Rekomendacja: dodać realne pliki do public/: OG 1200 x 630, favicon SVG i apple touch icon 180 x 180.

3. Rewrite łapie wszystko

Wysokie Vercel HTTP

Źródło: vercel.json:2-4

{ "source": "/(.*)", "destination": "/index.html" }

To jest wygodne dla SPA, ale niebezpieczne dla assetów. Brakujące obrazy, ikony i potencjalnie inne pliki zwracają index.html, a nagłówki dla rozszerzeń ustawiają cache immutable.

Rekomendacja: fallback SPA powinien dotyczyć tylko dokumentów, a nie plików z rozszerzeniami.

4. hreflang deklaruje /pl, ale trasy nie ma

Wysokie i18n SEO

Język działa jako stan Reacta, domyślnie EN. Nie ma route /pl, /pl/services, itd. Live /pl zwraca index.html, ale po stronie klienta wpada w 404.

Rekomendacja: usunąć hreflang="pl" do czasu wdrożenia URL-i językowych albo dodać realny routing /pl.

SEO i indeksacja

Mocne strony

  • Jest sitemap i robots.
  • Jest llms.txt.
  • Jest rozbudowane schema.org: Person, Organization, WebSite, ProfessionalService, FAQ, BlogPosting.
  • Każda główna trasa ma unikalne title/description w getPageSEO.
  • Sitemap zawiera core pages, case studies, journal i service details.

Problemy

  1. Fallback HTML z index.html jest jedynym statycznym dokumentem dla wszystkich tras.
  2. og:image domyślnie wskazuje brakujący plik.
  3. Organization.logo wskazuje OG image zamiast prawdziwego logo.
  4. FAQPage na homepage może być ryzykowne, jeżeli pytania/odpowiedzi nie są widoczne na stronie w takiej samej formie.
  5. reviewsSchema i aggregateRating wymagają ostrożności: recenzje powinny być realnie widoczne i udokumentowane.

Rekomendacja strategiczna: jeśli SEO/LLM discovery jest ważne, rozważyć prerender/SSG dla głównych tras. Największy zysk: prawdziwe HTML dla /services, /process, /glossary, /work/* i /journal/*.

Performance

Build przechodzi, ale największe ryzyka to ciężkie assety i globalne efekty.

Największe obciążenia

  • dist/assets/bkg1 2-*.png około 9.1 MB
  • RP4 około 4.5 MB
  • BP4 około 3.3 MB
  • kilka kolejnych PNG 1-2.6 MB
  • dist po buildzie około 77 MB
  • public/videos około 8.8 MB
  • public/scroll-frames około 5.1 MB
  • public/scroll-frames-light około 2.1 MB
  • główny JS około 429 KB, gzip 127 KB
  • CSS około 278 KB, gzip 47 KB

Rekomendacje

  1. Skonwertować największe PNG do AVIF/WebP i użyć responsive sizes.
  2. Przejrzeć, czy duże assety są importowane na homepage lub przez komponenty globalne.
  3. Dodać budżety bundle size w CI lub prosty skrypt raportujący top 20 assetów.
  4. Ograniczyć zewnętrzne fonty: Fontshare, cdnfonts i Google Fonts to trzy osobne źródła.
  5. Przemyśleć preloader, bo blokuje body na start przez około 800 ms plus animację.

UX / konwersja

Mocne strony

  • Bardzo wyrazisty positioning: design partner, operating system, r3loop.
  • Jest wiele ścieżek kontaktu: brief, Calendly, mail.
  • Case studies, services, process i glossary dobrze budują kategorię.
  • Floating CTA i chat mogą wspierać konwersję.

Ryzyka

  1. Zbyt dużo globalnych efektów nad każdą stroną: preloader, smooth scroll, cursor glow, custom cursor, persistent background, bottom gradient, floating CTA, chatbot.
  2. Header ma pointer-events-none gdy nie jest scrolled, z wyjątkami na elementach.
  3. Przełącznik języka nie aktualizuje URL-a, więc użytkownik nie może wysłać linku do polskiej wersji.
  4. Strony limitedaccess* są routowane publicznie. Jeśli to materiały prywatne, powinny być chronione po stronie serwera.

Accessibility

Plusy

  • Wiele przycisków ma aria-label.
  • Obrazy case studies mają alty.
  • Elementy dekoracyjne często mają aria-hidden.

Ryzyka

  1. Custom cursor i motion-heavy UI powinny być w pełni wyłączalne przy prefers-reduced-motion.
  2. Smooth scroll i animowane przejścia mogą przeszkadzać użytkownikom klawiatury/screen readerów, jeśli focus nie jest zarządzany po zmianie route.
  3. Mobile menu powinno mieć aria-expanded, aria-controls i focus trap.
  4. Chatbot/floating CTA mogą konkurować z główną nawigacją na małych ekranach.

Analityka i privacy

GTM jest wstrzykiwany przez React po mount: src/app/components/GTM.tsx. Plus: nie blokuje statycznego HTML.

Ryzyko: brak widocznej warstwy consent/cookies w kodzie, a GTM może ładować narzędzia wymagające zgody w UE. Przy lokalizacji w Hiszpanii/Mallorce warto sprawdzić zgodność z ePrivacy/GDPR.
